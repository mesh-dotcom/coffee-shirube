# 珈琲しるべ

好きな味のスペシャルティコーヒー豆を、お店をまたいで探せるサイトと、そのデータを毎日集める仕組みです。

- **好きな風味から選べる**：お店が書いているフレーバーの言葉を「果実・花・柑橘・紅茶・チョコ・ナッツ」の5つに振り分けて、味の好みから探せます。
- **こだわりでも絞れる**：産地・品種・精製・つくり手・お店でも絞り込めます。
- **いま買える豆だけ**：在庫のあるシングルオリジンだけを載せ、気になった豆はそのままお店のページへ飛べます。

名前の「しるべ」は、道しるべのことです。好きな味の豆までの道案内になれたら、という意味を込めています。

**費用はかかりません。** GitHub の Public リポジトリなら Actions と Pages は無料で、豆の情報の読み取りも API を使わないルールで行います。設定もふだんの運用も、GitHub の画面だけでできます。

## しくみ

1. 毎日 3:00（日本時間）に、GitHub Actions が各店のオンラインストアから商品の一覧を取ります。
2. 商品の説明と商品ページの仕様欄から、産地・品種・精製・風味などの事実だけを読み取り、`data/beans.json` に保存します。
3. サイト（`index.html`）は `data/beans.json` を読んで表示します。GitHub Pages が公開します。

## はじめかた

1. 先に [`docs/legal-checklist.md`](docs/legal-checklist.md) の「👤 運営者の作業」を読みます（文化庁の資料を読む、各店の利用規約を目で確かめる、連絡先を用意する）。
2. GitHub で **Public** のリポジトリを作り、このフォルダの中身をすべて置きます。`.github` フォルダと `.nojekyll` も忘れずに（Mac の Finder では ⌘ + Shift + . で表示されます）。
3. **Settings → Secrets and variables → Actions → Variables** で、`CONTACT_URL` にお問い合わせ先（専用のメールアドレスかフォームのURL）を登録します。サイトの「お問い合わせ・掲載の停止」と、収集ボットの名乗りに使います。登録しなければ、リポジトリの Issues を案内します。
4. **Settings → Pages** で「Deploy from a branch」→ `main` / `(root)` を選びます。
5. **Actions** タブ →「豆データの収集」→ **Run workflow**。10〜20分で終わり、数分後に `https://ユーザー名.github.io/リポジトリ名/` に反映されます。

以降は毎日 3:00 に自動で集めます。

## ふだんの運用

### 毎回の結果を見る

**Actions** タブで実行を開くと、ページの下に「豆データの収集」のまとめが出ます。

- お店ごとの掲載件数と、風味・品種・精製が読めた件数
- 取得できなかったお店と、その理由
- 「確認のお願い」（利用規約をまだ目で確かめていないお店、規約が変わったお店）

失敗したときは、GitHub からメールが届きます。

### 毎日の点検と修正

毎日の収集が終わると、結果を自動で点検します（`scripts/health.mjs`）。次のようなときは「問題あり」とし、実行を失敗にしたうえで、ラベル「自動チェック」の Issue を作ります（開いていれば追記）。

- 取得できなかったお店がある
- 豆が1つも載っていないお店がある、または前回から半分以下に減った
- 価格が ¥300 未満・¥60,000 超（ドルなど、円以外で載っている疑い）
- データが30時間以上更新されていない

問題が無くなった回に、その Issue は自動で閉じます。毎朝、Claude の定期実行（claude.ai の Routines）がこの Issue を見て原因を調べ、直せるものは修正のプルリクエストを出します。中身を見て **Merge** すれば反映されます。

### お店を足す・止める・規約の確認を記録する

**Actions** タブ →「お店の管理」→ **Run workflow** のフォームからできます。終わると、そのお店の分だけすぐサイトに反映されます。

| やること | 入れるもの | 何が起きるか |
|---|---|---|
| お店を足す | オンラインストアのURL（店名は空でもよい） | お店を登録し、利用規約を自動で判定します。禁止が見つからなければ、その場で集めはじめます |
| お店を止める | id・URL・店名のどれか | そのお店の豆が、すぐサイトから消えます。掲載の停止を頼まれたときに使います |
| お店を再開する | 同上 | 止めたお店をもう一度集めます |
| 規約を確認した（掲載してよい） | 同上 | 規約を自分で読んで、自動収集の禁止がなかったときに記録します |
| 規約で禁止されていた | 同上 | 集めないお店として記録します |
| 掲載の許諾をもらった | 同上（メモに日付と方法） | お店から許諾をもらったときに記録します。規約の内容にかかわらず集めます |

- 自動の判定は目安です。「確認のお願い」に出たお店は、規約を読んで「規約を確認した」か「規約で禁止されていた」を記録してください。
- Shopify 以外のお店を足すときは、フォームの「豆の一覧ページのURL」も入れます。
- `data/shops.json` を直接書きかえても同じことができます。送料や所在地（`shipping`・`area`・`style`）は、このファイルに書くとサイトの「お店ごと」に出ます。

### 規約の見張り

集めているお店の規約ページは、30日ごとに自動で読みなおします。自動収集を禁止する書き方が加わっていたら、そのお店の収集を止めて「確認のお願い」に出します。

## サイトを直す

`index.html` を GitHub 上で編集して Commit すると、数分で反映されます。`<script>` の先頭で変えられるもの:

| 項目 | 内容 |
|---|---|
| `CONTACT` | お問い合わせ先。空なら `CONTACT_URL` の値、それも無ければリポジトリの Issues を案内します |
| `NEW_DAYS` | 「NEW」を付ける日数（既定 14日） |
| `TASTES` | 風味の5分類と、それぞれに振り分ける言葉 |

## 読み取りのルールを直す

読み取りは `scripts/rules.mjs` のルールで行います。「品種：」「Variety:」のような見出しと、産地・品種・風味の言葉の辞書を使い、説明に見出しが無いお店は商品ページの仕様欄から読みます。

実行結果のまとめで「読めた件数」が少ないお店は、書き方がルールに合っていません。次を足して `RULES_VERSION` を上げると、読みなおします。

- 見出しの言葉 → `LABELS`
- 産地・品種・風味・地域の言葉 → `COUNTRIES`・`VARIETIES`・`FLAVORS`・`REGION_JA`

`FLAVORS` に風味の言葉を足したら、`index.html` の `TASTES` にも同じ言葉が入っているか、テスト（`npm test`）が確かめます。

## 収集のルール

- 残すのは、産地・品種・精製・価格などの事実の項目と、商品ページのURLだけです。商品説明の文章や写真は保存しません。風味は16字以内の単語だけを残します。
- 利用規約の確認が済んだお店だけを集めます。自動収集を禁止しているお店や、判断がつかないお店は集めません。
- `robots.txt` を守ります（自分あての `CoffeeShirubeBot` の指定を優先）。robots.txt がサーバーエラーのときは、そのお店から何も取りません。
- ページの noindex（`meta robots`・`X-Robots-Tag`）に従います。商品ページは、初めて載せるときと、その後2〜3週間ごとに確かめます。ログインやパスワードのページへ転送されたら取得しません。
- 同じお店へのアクセスは3秒以上あけ、`Crawl-delay` が長ければそちらに従います（30秒より長い指定のお店からは取得しません）。429やサーバーエラーが返ったら、そのお店はその日の収集を打ち切ります。
- 価格と在庫は毎日の一覧から更新します。値段が変わっただけなら、商品ページは開きません。
- 価格は円で受け取ります。収集を動かす GitHub のサーバーはアメリカにあるため、見る人の国で通貨を切りかえるお店（Shopify の Markets）には「日本・円で見ている」と伝えます。それでも円以外で返ってきたお店は、間違った価格を出さないよう、その日は豆を載せません。
- 豆ごとに、初めて載った日（`firstSeen`）と確かめた日（`checkedAt`）を残します。取得できなかった日は7日以内に確かめた豆だけを残し、サイトのカードに確かめた日を出します。
- 売り切れ・ブレンド・ドリップバッグ・セット・定期便・器具は載せません（ブレンドも載せたいときは `INCLUDE_BLENDS=1`）。
- ページに書かれていない項目は推測で埋めず、空欄のままにします。

## Claude API も使うとき（任意）

API キーを登録すると、次の2つができます。使わなければ、この章は飛ばしてください。

- **読めなかった商品の補完**：Variables に `EXTRACTOR` = `hybrid` を登録すると、ルールで産地や風味がほとんど読めなかった商品だけ Claude が読みます。規約の判定も Claude が行います。
- **新しいお店探し**：「豆データの収集」の Run workflow で「新しいお店も探して追加する」にチェックを入れます。

キーは Claude Console で作ってクレジットを購入し、**Settings → Secrets and variables → Actions → New repository secret** に `ANTHROPIC_API_KEY` として登録します。

## 収益化するとき

- `data/shops.json` の `"commercial"` を `true` にします。規約で情報の商業利用を禁止しているお店は、自動で対象外になります（いまは LIGHT UP COFFEE）。続けて載せるには許諾をもらい、「掲載の許諾をもらった」を記録します。
- 有料掲載のお店には `"ad": "paid"`、アフィリエイトリンクのお店には `"ad": "affiliate"` を付けます。サイトのカードとお店の見出しに「PR」が出て、結果の上に説明が出ます。おすすめ順は変わりません。
- アクセス解析や広告のタグを入れるときは、`index.html` のフッター「外部送信について」に送り先・送られる情報・目的を書き足します。

くわしくは [`docs/legal-checklist.md`](docs/legal-checklist.md) の「収益化する前にやること」を見てください。

## ファイル

| ファイル | 役割 |
|---|---|
| `index.html` | サイト本体。`data/beans.json` を読んで表示します（まだ無いときは「準備中」と表示） |
| `data/shops.json` | 収集するお店の一覧と、利用規約の確認結果 |
| `data/beans.json`・`data/cache.json` | 集めた豆のデータと、読み取り結果の控え（自動で作られます） |
| `data/candidates.json` | お店探しで見つけた候補（お店探しを使ったときだけ作られます） |
| `scripts/collect.mjs` | 各店の商品を集めて `data/beans.json` を作る |
| `scripts/lib.mjs` | 共通の部品（robots.txt の確認、間をあけた取得、Shopify の一覧、Claude API の呼び出し） |
| `scripts/rules.mjs` | 読み取りのルール（見出し、言葉の辞書、利用規約のキーワード） |
| `scripts/terms.mjs` | 利用規約の判定と見張り |
| `scripts/manage.mjs` | 「お店の管理」のフォームの中身 |
| `scripts/discover.mjs` | Claude の Web 検索で新しいお店を探す（API キーが必要） |
| `.github/workflows/` | 「豆データの収集」（毎日 3:00）と「お店の管理」（フォーム） |
| `scripts/health.mjs` | 毎日の収集のあとに結果を点検する（お店の取得失敗・豆の急な減少・不自然な価格・更新の停止） |
| `.github/report-health.sh` | 点検で問題があれば「自動チェック」の Issue で知らせ、直ったら閉じる |
| `.github/save-data.sh` | 集めたデータ（`data/`）をコミットして保存する。手での編集と重なったときは、手での編集を優先します |
| `.nojekyll` | GitHub Pages にファイルをそのまま公開させるための空のファイル（消さないでください） |
| `package.json` | `npm test` などのコマンドの定義（依存パッケージはありません） |
| `docs/legal-checklist.md` | 著作権・景品表示法・価格表示・外部送信・商標についての確認リスト |
| `tests/` | 偽のお店で流れを確かめるテスト（ネット接続・APIキー不要） |

## 手元で動かす（Node 20 以上。しなくても運用できます）

```bash
node scripts/collect.mjs --shop lightup     # 1店だけ集める
node scripts/collect.mjs --dry-run          # 保存せずに、新しく読む商品の数だけ数える
node scripts/collect.mjs --probe https://example-coffee.jp/   # 読み取れるお店か確かめる
node scripts/manage.mjs add https://example-coffee.jp/         # お店を足す
node scripts/terms.mjs --list               # 利用規約の判定の一覧
python3 -m http.server                      # http://localhost:8000 で表示を確認
npm test                                    # テスト
```

| 環境変数（GitHub では Variables） | 既定 | 内容 |
|---|---|---|
| `CONTACT_URL` | リポジトリの Issues | お問い合わせ先 |
| `EXTRACTOR` | `rules` | 読み取りの方法。`rules`（API なし）、`hybrid`（読めなかった商品だけ Claude）、`claude`（すべて Claude） |
| `CLAUDE_MODEL` | `claude-haiku-5-5` | 読み取りと規約の判定に使うモデル |
| `CLAUDE_TERMS_MODEL` | `CLAUDE_MODEL` と同じ | 規約の判定だけ別のモデルにしたいときに使う |
| `CLAUDE_DISCOVER_MODEL` | `claude-sonnet-5-5` | お店探しに使うモデル |
| `MAX_NEW_EXTRACTIONS` | `150` | 1回で新しく読み取る・確かめなおす商品数の上限。残りは次回に回ります |
| `INCLUDE_BLENDS` | なし | `1` でブレンドも載せる |
| `REQUEST_GAP_MS` | `3000` | 同じお店へのアクセス間隔 |

## うまくいかないとき

- **サイトが「準備中」のまま** → 「豆データの収集」が終わっているか、`data/beans.json` ができているかを確かめます。
- **「変更を保存する」で失敗する** → **Settings → Actions → General → Workflow permissions** を「Read and write permissions」にします（ふつうは設定しなくても動きます）。
- **お店が「対象外」になる** → 実行結果の理由を見ます。利用規約の確認がまだなら、規約を読んで「お店の管理」で記録します。
- **お店が「取得できませんでした」になる** → お店の robots.txt や noindex で断られているか、一時的に混んでいます。7日以内に確かめた情報は載ったままです。
- **お店探しで失敗する** → 失敗しても、豆の収集はそのまま続きます（実行結果に警告が出ます）。API キーが必要です。キーがあるなら、Claude Console で Web 検索ツールの利用が許可されているか確かめます。
